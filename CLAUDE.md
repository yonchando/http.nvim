# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

http.nvim is a Neovim plugin (pure Lua, LuaJIT) for browsing a Postman collection and editing its requests as `.http` (JetBrains HTTP Client format) buffers. This branch is a **rewrite in progress**: the v1 implementation (Go helper binary + `cmd.lua`/`ui.lua`/`log.lua`/`floating/window.lua`, `plugin/load_http.lua`) has been removed but is still available in git history (the `main` branch) for reference. `README.md` documents the rewrite; keep it in sync with the help file. The rewrite sends a request with `curl` from the panel or an edit buffer (`<leader>hrr`), replacing `{{key}}` with environment values.

## Architecture

- `plugin/http.lua`: the auto-loaded entrypoint. It registers `:Http` / `:Http create {name}` and the `:HttpCookies*` commands, sets the global keymaps with `map_global_keys()` (`<leader>ho` open, `<leader>hrp`/`<leader>hre` show or resend the last request from anywhere), and runs `helptags` on VimEnter for a hardcoded path (`stdpath("data")/site/pack/chando/start/http.nvim/doc`).
- `lua/http-nvim/init.lua`: the public API only (`open`, `preview_last`, `run_last`, `setup`), forwarding to the modules below.
- `lua/http-nvim/state.lua`: the one shared `state` table (class `State`). Every module requires it and reads or writes it directly. It also holds the options: `collection_dir` (set by `setup({ collection_dir })`, default `stdpath("data")/http-nvim/collections`), `selected` (the chosen collection's folder name) and the derived `collection_path`/`env_path`/`cookie_path`.
- `lua/http-nvim/config.lua`: only the `ns` extmark namespace.
- `lua/http-nvim/keymaps.lua`: every keymap, by action name (`defaults`). `setup({ keymaps })` calls `configure` (an action given replaces its default keys; `false` unmaps). Buffers map with `keymaps.map(action, rhs, bufnr)`; the global ones (`open`, `preview_last`, `run_last`) go through `apply_global`, which `plugin/http.lua` calls via `map_global_keys()` and `setup()` calls again so the order of the two doesn't matter. Never call `vim.keymap.set` directly.
- `lua/http-nvim/collections.lua`: one folder per collection in `collection_dir`. `create(name)` (`:Http create`), `list()`, `pick(on_done)` (`vim.ui.select`, used by `:Http` and by `open()` when nothing is selected) and `select(name)`. Switching closes the panel and the old edit buffers (`request_edit.close_edit_bufs`, which refuses if one is modified) and resets `state.collection`.
- `lua/http-nvim/collection.lua`: the Postman types, loading and writing the collection, the undo file for deletions, and tree helpers (`locate`, `ensure_folders`, `count_requests`, ...).
- `lua/http-nvim/env.lua`: loading, writing and parsing environment variables, and `expand_env` for `{{key}}` (and `{{$name(args)}}`, made by `dynamic.eval`; a failing or unknown one is left as is).
- `lua/http-nvim/json.lua`: a JSON scanner/checker/formatter that works on the text (no `vim.json`, which loses key order): `check(text)` gives `JsonProblem`s (the first error, plus `warning` ones for comments and duplicate keys), `format(text, indent)` keeps key order, values and comments, and `{{...}}` outside a string is a value. Used by the LSP (diagnostics, formatting) and by `request.lua`'s send-time warning.
- `lua/http-nvim/dynamic.lua`: the dynamic variables (`variables`: `make(args)`, snippet `args`, `doc`; `eval(text)` returns `value, err, known`), named after JetBrains' (`$uuid`, `$timestamp`, `$isoTimestamp`, `$randomInt`, `$random.uuid/integer/float/alphabetic/alphanumeric/hexadecimal/email`). Used by `handler.lua`, `env.lua` and the LSP's completion and hover.
- `lua/http-nvim/request.lua`: curl (`send_request(request, scripts, node)`, with `state.cookie_path` as its `--cookie`/`--cookie-jar`), the response layout, `preview_last`/`run_last`. `scripts_for(node, own)` builds the `RequestScripts` (`prerequest`/`test` lists: the collection's, each folder's from `collection.ancestors`, then the request's own). `curl_args` also returns the body as sent: `check_json_body` warns when a JSON `Content-Type` comes with a body that doesn't decode, and `with_sent_body` puts it (as `> ` lines) after the first request-header block of the headers box. It runs the `prerequest` ones through `handler.lua` before building the curl args (so `{{key}}` sees what they set), and the `test` ones after the response.
- `lua/http-nvim/cookies.lua`: the selected collection's curl cookie jar (`state.cookie_path`, `<collection_dir>/<selected>/cookie`, set by `collections.select`), parsed as Netscape cookie lines. Backs `:HttpCookies` (masked popup), `:HttpCookiesClear` (deletes the file), `:HttpCookiesDelete {name}` and `:HttpCookiesEdit`.
- `lua/http-nvim/handler.lua`: pre-request (`< {% %}`) and response handler (`> {% %}`) scripts. No JS engine: it only reads `client.global.set("key", expr)` and `client.global.secret(...)` calls (the JetBrains API only, no `request.variables` or Postman `pm.*`; `.secret` sets the type `secret`), evaluates `expr` (`response.body.a[0]`, `response.status`, `response.headers.valueOf()`, `response.cookies()`/`cookiesByName()` from the `Set-Cookie` lines, `client.global.get()`, a `$name` dynamic variable through `dynamic.eval`, `decodeURIComponent()`/`encodeURIComponent()` around a value, literals joined with `+`; `response.*` is an error before the request) and saves the keys with `env.set_vars`. `run(scripts, response)` takes a list of scripts, runs them in order (a later one's `get` sees what an earlier one set) and saves once. Before a request it also returns the `request.headers.set("Name", expr)` calls, which `request.lua`'s `with_headers` applies to a copy of the request (replacing enabled headers of that name, case-insensitive, else adding); in a response handler that call is an error. Scripts are stored as Postman `prerequest`/`test` events (`jetbrains.script_of(item, listen)`/`set_script(item, script, listen)`), on requests, folders and the collection root.
- `lua/http-nvim/lsp.lua`: an in-process language server (`vim.lsp.start` with a `cmd` function), attached to each request edit buffer by `edit()` and each scripts buffer (`b:http_nvim_scripts`, where only script completion applies). Completion (`{{key}}` env vars, methods, headers and values, cookie names from `cookies.list()` in a `Cookie:` header and `response.cookiesByName("")`, the script API inside `< {% %}` (no `response.*`, plus `request.headers.set`) and `> {% %}`, and env names in `client.global.get("")`) and hover on `{{key}}` (its value, masked when secret). It reads the buffer through the Neovim API instead of keeping the text from `didChange`, and uses `utf-8` positions. JSON bodies (found by `json_bodies`: after the headers, up to a `> ` handler or the next `###`; JSON by `Content-Type`, or by a leading `{`/`[` without one) get diagnostics, pushed with `publishDiagnostics` after each `didOpen`/`didChange` (it advertises `textDocumentSync` only to hear about changes), and `textDocument/formatting` edits (indent from the request's `tabSize`/`insertSpaces`). `setup({ lsp })` sets `state.lsp` (`false` off, `autotrigger` turns on `vim.lsp.completion`).
- `lua/http-nvim/request_edit.lua`: request and environment edit buffers (`e`), and scripts buffers (`S`, `edit_scripts_at_cursor`): `http-nvim-scripts://<folder path>` (empty path for the collection) holding a `< {% %}` and a `> {% %}` block, parsed with `jetbrains.script_blocks` and kept in `state.script_bufs` (closed and renamed with the request edit buffers). It requires `panel` lazily, inside `render()`, because `panel` requires it.
- `lua/http-nvim/panel.lua`: rendering the panel and its keymaps (`open`).

How the panel and edit buffers work:
  - **Loading:** the collection is loaded once into `state.collection`, with `state.items` set to `collection.item`. The path is `state.collection_path`, i.e. `<collection_dir>/<selected>/collection.json`; a missing file starts an empty collection, created on the first save. Edits survive closing and reopening the panel because the collection isn't reloaded. Environment variables are loaded at the same time from `state.env_path`, a Postman environment, into `state.env`: its `values` list of `EnvVar` (`key`, `value`, `type`, `enabled`; other fields are kept). The older `{ "values": { key = value } }` map is still read and saved in Postman's shape. They are listed in file order as `KEY = value` lines under "Environment variables", disabled ones as `# KEY = value`, which `expand_env` skips.
  - **Panel:** a nui.nvim `Split`, filetype `http-nvim`.
  - **Rendering:** `render()` rebuilds the lines and fills `state.line_nodes` and `state.line_paths` (both keyed by line number). Keymaps use them to find the item under the cursor. Folder expansion is kept in `state.expanded`, keyed by node table.
  - **`e` (`edit()`):** opens the request in an `aboveleft split` of the panel. The buffer is named `http-nvim://<path>` and uses `buftype=acwrite`, `filetype=http`.
    - Closing that window moves focus back to the panel (a `WinClosed` autocmd).
    - An unloaded leftover buffer with the same name is wiped and rebuilt.
    - Buffers are made by `create_edit_buf`. An untracked, unmodified buffer with the same name is wiped. If the name is taken by another tracked edit buffer (e.g. two requests with the same path) or by a modified buffer, it refuses before opening the split. `nvim_buf_set_name` would throw and leave a nameless listed buffer, which breaks `:wa` (E141).
  - **Saving an edit buffer (`BufWriteCmd`):**
    - It parses the buffer with `jetbrains.from_lines` and deletes every section except the first named one.
    - The `### name` line renames the item, and the buffer is renamed to match.
    - It then rewrites the whole collection file with `vim.json.encode` (4-space indent, sorted keys).
    - Vim skips `BufWritePre`/`BufWritePost` for a buffer with a `BufWriteCmd`, so every edit buffer's handler fires them itself (`fire_write`): `BufWritePre` before reading the lines (format-on-save plugins such as conform.nvim run there), `BufWritePost` only after a successful save. A request buffer then formats its JSON bodies with `lsp.format_bodies` when `state.format_on_save` (`setup({ format_on_save })`, default true).
- `lua/http-nvim/jetbrains.lua`: converts between Postman requests and JetBrains HTTP format.
  - `to_lines` writes a request out. Disabled headers become `# Key: value` comments. A non-raw body becomes a comment saying it is kept as is.
  - `from_lines(lines, original)` parses with **tree-sitter** (the `http` grammar). It uses only the first `(section (request_separator) (request))` and returns `request, err, { name, start_row, end_row }, script, pre_script` (the `> {% %}` and `< {% %}` lines, or nil). The pre-request script sits between `### name` and the request line and is read from the text with `script_blocks`.
  - Fields the HTTP format can't express are copied from `original`. A non-raw body is left untouched.
  - Grammar quirks: a header with a one-letter name (`A: 1`) is parsed as a new request, disabled headers arrive as `comment` nodes, a one-line `> {% ... %}` isn't parsed as a `script` (the handler is read from the `res_handler_script` text instead), and a one-line `< {% ... %}` breaks the section (`from_lines` blanks it before parsing). A header without `:` or without a value also ends the request early: `from_lines` refuses the first (found by `header_rows`) and parses the second with a stand-in value. Any non-blank line the grammar leaves outside the section, before the next `###`, makes `from_lines` fail, because saving drops everything outside the first section.
- `syntax/http-nvim.vim`: highlight groups for the panel (documented in the help file).
- `syntax/http-nvim-scripts.vim`: the fallback highlighting for scripts buffers (JavaScript inside `< {% %}`/`> {% %}` via `syn include`), used when the tree-sitter `javascript` parser is missing. The http grammar only reads a `> {% %}` block after a request line, so `highlight_scripts` (in `request_edit.lua`) instead gives the buffer a `javascript` parser limited by `set_included_regions` to the code of each block, one region per block, recomputed on `on_lines`. It replaces the http highlighter with `vim.treesitter.highlighter.new`, and extmarks highlight the markers and `#` comments.
- `doc/http-nvim.txt`: the vim help file. Keep it in sync with keymaps and behavior; `doc/tags` is generated by `:helptags`.

Postman v2.1 shapes to handle: `request` may be a bare URL string (method defaults to GET), and `url` may be a string or `{ raw = ... }`. JSON is decoded with `luanil` for objects and arrays, so `null` fields disappear.

## Development

There is no build step, test suite, or linter config beyond `.luarc.json` (lua-language-server: LuaJIT runtime, `vim` global, strict table shapes). Runtime requirements: Neovim with the tree-sitter `http` parser (`:TSInstall http`) and nui.nvim.

Run the plugin locally:

```sh
nvim --cmd "set rtp+=." --cmd "set rtp+=/path/to/nui.nvim" test.http
```

To check behavior without a UI, write a Lua script and run it headless. Drive keymaps with `nvim_feedkeys(..., "x", false)`.

```sh
nvim --headless --cmd "set rtp+=. rtp+=/path/to/nui.nvim" -c "luafile script.lua" -c "qa!"
```

The test fixtures are `tests/collection.json` and `tests/env.json`, i.e. the collection `tests` with the repo root as `collection_dir`. Load them in a headless script with `require("http-nvim").setup({ collection_dir = vim.fn.getcwd() })` then `require("http-nvim.collections").select("tests")`. Saving rewrites them, so back them up before testing saves and restore them afterwards. To keep a headless test away from the real `stdpath("data")`, set `XDG_DATA_HOME` to a scratch folder and run with `--clean` (otherwise the user config reinstalls its plugins there), adding `~/.local/share/nvim/site` to `rtp` for the tree-sitter `http` parser and running `runtime plugin/http.lua` for the commands and keymaps. `*.http` files are gitignored, so scratch request files can live in the repo root.
